# weave-viewer-cli v0.1.5 — `--record` SIGABRTs silently on default-font miss

**Tested:** `weave-viewer-cli 0.1.5` macOS arm64 (Homebrew tap, sha256 `b3c590dd…b6dfc`)
**Regression vs:** v0.1.4 (same warning was non-fatal there)
**Severity:** blocker — every template that lays out text crashes `--record`

## TL;DR

A failed lookup of the engine's default font `GoogleSansCode` is now fatal to
`--record`. The process aborts with SIGABRT (exit 134) without a panic, without
a backtrace — just one warning line on stderr before death:

```
[warning] [css_engine::google_fonts] google-fonts: no source found for 'GoogleSansCode'
```

`--validate` does not exercise the font-load path and returns 0 cleanly, so the
breakage is invisible to pre-flight checks. Affects any non-trivial template.

## Repro (one paste — exits 134 every time)

```bash
mkdir -p /tmp/v015-font-repro && cd /tmp/v015-font-repro

cat > template.weave <<'HTML'
<!DOCTYPE html><html><body><div>weave ok</div></body></html>
HTML

cat > manifest.json <<'JSON'
{ "render": { "width": 320, "height": 240, "fps": 24, "duration": 1 } }
JSON

weave-viewer-cli . --record out.mp4
echo "exit=$?"
# exit=134
# Only stderr line:
#   [warning] [css_engine::google_fonts] google-fonts: no source found for 'GoogleSansCode'
# out.mp4 is 0 bytes or a sub-1KB ffmpeg stub depending on encoder-pipe timing —
# never a real frame.

weave-viewer-cli . --validate
echo "exit=$?"
# exit=0   ← validator does not exercise the font load
```

## Observed vs expected

| | Observed | Expected |
|---|---|---|
| Exit code | 134 (SIGABRT) | 0 with a fallback font |
| Stderr | one warning, no panic, no backtrace | warning + continue, or a clean error message before abort |
| Output mp4 | 0-byte or sub-1KB ffmpeg stub (no frames) | real 24-frame render with a fallback face |
| `--validate` | 0 (silent) | should flag if the font load will fatal at render time |

## Isolation matrix

Every case that emits the `GoogleSansCode` warning aborts; the single case that
doesn't emit it succeeds. `<video>` presence is incidental — it only "saves"
templates that happen to render zero text (no font load triggered).

| Template body | Triggers `GoogleSansCode` warning | Exit |
|---|---|---|
| `<div>weave ok</div>` (default font, text) | yes | **134** |
| `<body></body>` (no content at all) | yes | **134** |
| `<p>hi</p>` (default font, text) | yes | **134** |
| `<body style="font-family:sans-serif">…</body>` | yes | **134** |
| `<body style="font-family:sans-serif"><video …></video>…</body>` | yes | **134** |
| `<body style="background:#222"><video …></video></body>` (no text) | **no** | **0** |

The fact that `<body></body>` (literally empty) also crashes means the font lookup
fires during render init, not in response to a layout box that needs the font.

## Comparison with v0.1.4

v0.1.4 on the same templates emitted the analogous warning:

```
[warning] [css_engine::google_fonts] google-fonts: no source found for 'sans-serif'
```

…and **finished cleanly with exit 0 and a real mp4**. So either v0.1.5 changed
the default fallback name to one that always misses (`GoogleSansCode`), or it
changed a missed google-font lookup from a warning-and-fall-through to a fatal,
or both.

## Likely fix surface

The `css_engine::google_fonts` module's missed-source path. Either:

1. Ship `GoogleSansCode` (or a sane fallback) inside the binary's
   `data/fonts/` bundle so the lookup hits.
2. Make a missed google-font fall through to a bundled metric-compatible
   system face and continue, mirroring v0.1.4 behavior.
3. If the abort is intentional, emit a panic or error log line before
   `std::process::abort` so the failure mode is debuggable from a bug report.

Even just (3) would make this discoverable. (1) or (2) would make the binary
usable for templates that don't ship their own `@font-face`.

Bonus ask: have `--validate` exercise the same font-load path it would at
render time so consumers can pre-flight.
